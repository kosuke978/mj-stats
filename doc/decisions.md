# 意思決定記録

この文書は、開発者が決めた方針と、まだ決めていない設計上の選択の正本である。1つの判断ごとにファイルを増やさず、この文書にまとめる。ロードマップは順序、要件は満たす条件、ここは選択肢・決定・影響を扱う。

## 記録のルール

- `承認済み`：開発者が明示的に決定したもの。推奨案や回答待ちを含めない。
- 1つのD-IDに複数の条件がある場合は、承認済みの範囲と未決定の範囲を明記する。一部の回答だけで項目全体を承認済みにしない。
- `未決定`：仕様化・実装前に判断が必要。決定に依存する作業は止め、独立した準備を進める。
- `保留`：開発者が判断を後で行うと決めたもの。返答がないだけでは保留にしない。
- `置き換え済み`：後の決定で変更されたもの。前の判断と理由を削除せず、新しい判断へリンクする。

承認済みになったら、日付、決定者、具体的な採用内容、代替案、影響する要件・文書を記録する。判断した理由が開発者から示されていない場合は理由を推測して本人の発言として残さず、技術的な効果を別に説明する。

### D-04 Auth UIDと永続参加者ID

- 状態・決定者：承認済み。開発者、2026-10-06。
- 決定：参加者IDとSupabase AuthのUIDを分離する。ゲストも安定した参加者IDを持ち、後から登録しても同じIDの成績へ紐付ける。
- 検討した代替案：登録者の参加者IDをAuth UIDと同一にし、ゲスト登録時に履歴参照を移行。実DB調査後まで選択を保留。
- 効果・注意：認証されたUIDからアプリの参加者レコードへ対応付け、所属と成績の参照には参加者IDを使う。ゲストのAuth UIDは未設定を許容する設計とする。既存参加者IDがAuth UIDと同じ値でも、IDの一括振り直しを必要条件にしない。
- 確認した前提：users.idはUUIDのPK、既にauth_id UUID NULL UNIQUEがある。auth_idのAuth側FKはなく、現5参加者は未紐付け。Goはこの列を利用していない。
- 移行前提：既存列の活用、参照・RLS・Auth削除時の扱い、未紐付け参加者の本人確認を項目2〜4・11へ統合した。既存の対局・所属の参照を保つ。会話で承認されたのは設計方針であり、今回はDBを変更しない。
- 反映先：R-AUTH-02、R-GUEST-01、Q-08/Q-15。Step 1で対応関係を使う境界を実装し、Step 3でゲスト作成・登録連携の前提へ適用する。本人確認はD-15で運営承認を採用済み。複数の旧IDと登録参加者の対応モデルは項目9/11へ統合した。

### D-05 ゲストの再利用範囲と登録への案内

- 状態・決定者：承認済み。開発者、2026-10-10。
- 決定：未登録ゲストはリーグごとに管理し、同じリーグで同じ参加者IDを再利用する。複数リーグで継続利用したい人にはユーザー登録を案内し、登録者として同じアカウントで各リーグへ参加する形を促す。
- 検討した代替案：未登録ゲストのIDを複数リーグで共有する。
- 開発者の意図：「複数リーグになるならゲストではなく利用者になってほしい」「リーグごとに管理させて、もし複数リーグに入りたいならユーザー登録したら」という方針。
- 設計への反映：別リーグのゲストを共通一覧から選ぶ機能は提供しない。名前一致で同一人と判断せず、同じリーグ内でも同名の別人は別IDとする。成績・閲覧・記録権限はリーグごとの境界を維持する。ゲスト参加自体は認証済み記録者が保存できる要求を維持する。
- 境界：登録を促す方針であり、名前等で未登録の同一人を追跡し、別リーグでのゲスト参加を自動的に禁止する仕様を追加したものではない。登録後の過去成績はD-04に従って保全し、本人紐付けD-15と関連D-18で具体化する。
- 反映先：R-GUEST-01、[architecture.md](architecture.md)、Q-15、項目10の案内と登録導線。今回は登録案内・ゲスト永続化とも未実装。

### D-07 同点・点数単位・端数

- 状態・決定者：基本同点方針と100点単位・負点可を承認済み。開発者、2026-11-16。それぞれA案を採用。同日の追加回答で、成績を四捨五入する前提を置かないよう指摘を受けた。
- 決定した範囲：同点者を同順位とし、次の順位は人数分飛ばす。該当順位のウマを平均し、トップ同点時は総オカを等分する。35,000 / 35,000 / 20,000 / 10,000点の例では1/1/3/4位、30/30/−20/−40pt。素点は100点単位で負点を許す。ルールから求めた値を小数第1位へ四捨五入することを仕様にしない。
- 検討した代替案：座順等を使って同点者にも順位の優劣を付ける方式、1点単位の素点入力。
- 追加確認の訂正：AIは現行DBのnumeric(6,1)に合わせた丸めの2案（同point優先/合計0優先）を提示したが、どちらも採用されていない。現行の保存精度を競技ルールへ転用する前提を撤回する。通常の100点単位の素点換算には丸めが不要で、3人同点等の等分による循環小数とは区別する。
- 設計への反映：Goの計算・保存で同じ同点処理を使い、入力順による端数配分を行わない。等分した値を正確な分数で保存・集計する技術案を [設計確認5](architecture.md#同点計算と保存精度)へ具体化した。業務上の等分・非丸め方針を実現する手段として、分数の列/API型を総合レビューへ統合した。
- 具体化：負点/整数範囲、ルール許容値/初期設定、正確なn/d、循環小数の省略表示と分数確認、旧値保全・API/DB型を項目5/9〜11へ統合した。計算版と整数ウマの範囲は技術設計として総合レビューの対象にし、分析用の同点集計はPhase 3で確定する。
- 反映先：R-MATCH-01〜03/B-03、[architecture.md](architecture.md)、Q-01〜Q-03/Q-11/Q-12/Q-16。現行のmath.Round・入力順補正・numeric(6,1)は未解消の実装差分として維持する。

### D-13 保存の二重送信

- 状態・決定者：承認済み。開発者、2026-11-16。A案を採用。

### D-16 日時・タイムゾーン

