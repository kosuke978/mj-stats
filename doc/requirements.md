# 要件・業務ルール・利用フロー

この文書は「MJ-Statsが何を満たすべきか」の正本である。現行コードの挙動は [features-api.md](features-api.md)、実装順は [product-roadmap.md](product-roadmap.md)、仕様の選択は [decisions.md](decisions.md)、確認方法は [quality-and-acceptance.md](quality-and-acceptance.md) に分ける。

要件の掲載は、後続Stepの実装着手や新しい仕様案の承認ではない。必須要件はユーザーの最終構想と承認済みの指示に基づき、判断が必要な条件は未決定として扱う。

## 利用者と役割

| 利用者・概念 | したいこと | 区別すること |
| --- | --- | --- |
| 登録ユーザー | ログインし、参加した対局や所属コミュニティの成績を確認する | Authのアカウントと、成績の紐付け先である参加者レコード |
| 未登録ゲスト | アカウントを作らず、リーグ内で対局へ参加し成績を継続して残す。複数リーグで継続利用する場合は登録を案内する | ゲスト参加と、未認証のAPI操作。操作は権限のある登録ユーザーが行う。登録案内はD-05 |
| 対局参加者 | その卓の成績を持つ4人 | 操作者・記録者と一致するとは限らない |
| 記録者 | 対局と結果を入力する | D-12によりリーグ所属の登録者全員が代理記録可。本人が卓の参加者である必要はない |
| リーグ運営者 | 所属・ルール・シーズンを管理する | owner/adminの権限はリーグごとに決める。全サービス共通の管理者権限ではない |

登録ユーザーがログインできても、自動的に全リーグのメンバーにはならない。seedの固定ユーザーを本人アカウントとして扱わない。ゲスト名が同じでも同一人物とは判断しない。

D-05の登録案内は、ゲストを使う人へ複数リーグでの利用と過去成績の本人紐付けを説明するもの。文言案は『登録すると、同じアカウントで複数リーグに参加できます。ゲスト時代の成績は本人確認後に引き継げます』。登録を通常のゲスト記録の必須操作にせず、成績の閲覧範囲D-11を維持する。案内は項目10の入力/設定の導線に置き、本人確認の画面はD-15と目標画面設計に従う。

## 用語

| 用語 | このプロジェクトでの意味 |
| --- | --- |
| リーグ | サークル等のコミュニティ。所属・ルール・集計・権限の境界 |
| シーズン | リーグ内の集計期間。切り替えは過去成績の削除を意味しない |
| 対局 | 現在の入力単位は四麻1回分の最終成績。局ごとの和了・放銃イベントを保存する機能は現状ない |
| 素点・持ち点 | 終了時の点数。APIの `raw_score`、履歴の `score` に対応 |
| 返し点 | 成績ポイントの基礎計算で差し引く基準点 |
| ウマ | 順位に応じた加減点。D-07に従い、同点者が占める順位のウマを平均する |
| オカ | 開始時持ち点と返し点との差によるトップ加点。現行実装は合計20ポイントをトップへ配分する |
| 最終ポイント | 競技ルールに基づく成績。保存の `final_point`、APIの `point` に対応 |
| 精算ポイント | 飛び賞等も考慮するPhase 5の運用上の値。競技の最終ポイントとの関係を別途定義する |
| 役満・トビ | 成績分析・表示に用いる情報。発生条件、複数役満、0点の扱い等の詳細はPhase 3で確定する |
| 認証・認可 | 認証は操作主体の特定、認可は対象リーグで操作を許すかの判定 |

## 主な利用フローと受入の結果

### F-01 ログインして本人情報を使う

1. 初回は利用者が登録・メール確認を経てログインする。再訪時は保存したセッションを復元・検証し、利用可能ならログイン入力を省く（D-26/D-29）。
2. Webがセッションを扱い、GoがJWTを検証する。
3. meが本人のユーザーを作成または取得する。
4. 初回表示名が未設定なら本人が設定する。失敗時は入力を保持して再試行し、完了後は通常利用へ進む。再ログインで既存名を上書きしない（D-22）。
5. Web内から同じ本人情報を参照し、保護APIを呼び出す。

成功：本人の同じレコードを継続利用できる。失敗：認証不成立なら401またはログイン画面への誘導となり、他人のUIDで登録・保存しない。検証対象はR-AUTH-01〜04。

### F-02 対局を記録する

1. 記録者が、アクセス可能なリーグと適用ルール・対局日時を選ぶ。シーズンは指定するか未指定とする（D-16/D-17）。
2. 登録者または永続ゲスト4人を選び、素点を入力する。
3. Goの計算結果を確認する。現在の直接保存導線も、同じ検証・計算を経由する。
4. Goが保存時にも検証し、操作者から記録者を設定して一括保存する。
5. 保存された対局を履歴で確認する。

成功：4人の結果と適用条件・記録者が整合し、D-13に従い同じ保存操作の再送でも対局は1件。失敗：不正入力なら保存せず理由を返し、内部失敗なら部分保存を残さない。所属登録者の代理記録はD-12で許可済み。検証対象はR-LEAGUE-01、R-MATCH-01〜03、R-GUEST-01、Q-23。

### F-03 履歴を閲覧する

1. 認証済み利用者が閲覧対象のリーグ・期間を選ぶ。
2. Goが対象リーグへの所属を確認して履歴を返す。
3. Webが日時・表示名・成績を表示する。

成功：所属リーグのデータだけが表示され、同名・改名でも参加者IDを失わない。非所属の要求はGoで拒否する。0件は正常な空状態、取得失敗は再試行などの導線を持つ。検証対象はR-HISTORY-01、R-NAV-01。絞り込み・ページングの契約は対象Stepで設計する。

### F-04 リーグを見つけて参加・再参加する

1. 招待リンク、グループ番号、運営が掲載したリーグの名前検索から参加画面へ進む。リーグの作成時は検索非掲載とする（D-35）。
2. 必要な場合に登録・ログイン・初回表示名設定を済ませる。番号/検索の入口では参加コードを入力し、リンクでは招待資格を引き継ぐ。
3. 本人が参加を要求し、Goが要求時点の招待と本人を確認する。有効な招待があれば除名後の同じ本人も再参加できる（D-38）。
4. 所属成立後にリーグの成績へ進む。過去の参加者ID・成績を保ち、既に有効な所属を持つ場合は重複作成・roleの降格を行わない。

成功：入口が異なっても同じ所属・招待条件で参加できる。失敗：検索掲載や番号の一致だけでは所属を作らず、無効/失効/期限切れの招待では再参加も拒否する。除名後、再参加が成立するまでは閲覧・記録を拒否する。検証対象はR-LEAGUE-01、R-NAV-01、Q-14/Q-18/Q-19。除名は継続的な参加禁止ではなく、再参加はD-08のmemberとし、管理操作には項目8の権限表を適用する。

## 品質要求と未決定事項

- 安全性：認証不成立では保護APIを実行しない。リーグをまたぐ実データ運用には、承認した閲覧・記録範囲のGo側制御を必要とする。JWT保護だけで達成したと扱わない。
- データ信頼性：入力値から保存・履歴・集計まで参加者IDと計算条件を追跡でき、誤差や不正値を表示だけで隠さない。
- 操作性：入力を消さずに修正でき、保存中・失敗・空状態が分かる。狭い画面での操作とキーボード操作は、変更画面の受入確認に含める。
