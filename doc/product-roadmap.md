## 最終的に届ける体験

対象はwatnowなどの大学サークルや麻雀コミュニティ。点数を保存するだけでなく、「仲間とのライバル関係が見える分析」と「共有したくなるリザルト画像」を通じて、対局後も盛り上がれる体験をつくる。

| Phase | コアバリュー | 設計時に守ること |
| --- | --- | --- |
| 3 | 相性・天敵・カモの分析、トップ率・連対率・平均着順、役満・トビ、称号バッジ | 名前ではなく永続IDで参加者を追跡し、同卓関係と成績の原データを失わない |
| 4 | 対局結果・個人成績・レーダーチャートの動的SVG画像生成とSNS共有 | 集計データと描画を分け、画面とSVGの双方から同じデータを利用できるようにする |
| 5 | シーズンごとの成績切り替え・アーカイブ、ウマ・オカ・飛び賞による精算ポイント | リーグ・シーズン・適用ルール・操作主体を追跡し、過去結果を再現できるようにする |

SVG生成と、X・LINEへの投稿・プレビューで使用する出力形式の対応確認は別の工程である。SVGを生成できる設計を必須とし、必要な画像変換と共有方法はPhase 4で実証して決める。

将来に備えてデータと責務の境界を整えることは現在の作業に含む。未承認の分析、画像生成、精算、管理画面を先行実装することは含まない。

## 変更してはいけない条件

- `users`, `leagues`, `league_members`, `seasons`, `rules`, `matches`, `match_results` の7テーブルをプロダクトとして稼働させる。seedの存在だけで達成としない。
- 未登録ゲストもDBに永続化し、対局結果をユーザーIDに紐付ける。名前だけの保存や対局ごとに捨てるUUIDで済ませない。
- 持ち点合計、人数、参加者の重複、適用ルールなどの整合性をGo側でも検証する。フロントのチェックを信頼境界にしない。
- Phase 2.5はStep順に進める。現在Stepの完了報告と開発者の承認を得るまで、次Stepの実装に進まない。

## Step 1の実装対象

### バックエンド

1. JWTの署名と必要なclaimsを検証してから `sub` を読み、検証済みの認証主体をリクエストに引き継ぐ。`ParseUnverified` を認証に使わない。
2. 検証済みAuth UIDから対応する永続参加者を検索し、存在しない場合は信頼できるSupabase情報から作成する。D-04のID分離に従い、同じAuth UIDで繰り返し呼んでも重複させず、既存の参加者ID・表示名・履歴を維持する。
3. `/api/users/me`、対局保存、履歴取得、ポイント計算を共通の認証処理で保護する。`/api/health` のみ公開する（D-03で承認済み）。
4. 不正なJWTでDBへのユーザー作成や対局書き込みを行わない。DB障害などの内部エラーを認証エラーと混同しない。

### フロントエンド

1. メール・パスワードログイン、D-26の自己登録・メール確認後の導線、D-30のメールによるパスワード再設定を完成させ、成功・失敗・確認待ち・処理中を扱う。資格情報・確認処理はSupabase Authに任せる。
2. 保護ページへの直接アクセスを検証済みのセッションで判定し、未ログインなら `/login` に誘導する。
3. アプリ内で検証済みユーザーを参照できる共通の仕組みを用意する。具体的なProvider等の選択は実装設計で決める。
   D-22/D-24/D-25に従い、初回表示名設定と本人による名前変更を扱う。初回未設定は通常利用へ進ませず、Goでも制御する。長さ1〜30文字・同名可、変更後の履歴は現在名を表示する。
4. ブラウザからの計算・保存と、Server Componentからの履歴取得で、保護対象のGo APIへアクセストークンを送る。Next.jsのCookieは自動でGoのBearerヘッダーにはならない。
5. D-29に従い、保存済みセッションの復元・期限切れ後の更新・リダイレクト時のCookieを確認し、普段の再訪でログイン入力を求めない。ログアウトは任意操作とし、ユーザー固有のレスポンスを共有キャッシュへ流さない。

プロンプトは `middleware.ts` を指定していたが、現行Next.js 16では同規約が非推奨。[公式Proxy資料](https://nextjs.org/docs/app/api-reference/file-conventions/proxy) と `web/AGENTS.md` に沿い、D-09で `proxy.ts` への移行を開発者が承認済み。Step 1ブランチで移行・検証した。実行範囲と残る受入は品質文書を参照する。

作業ブランチの結果は [品質文書の検証記録](quality-and-acceptance.md#step-1実装ブランチの検証記録2026-11-17) に集約する。下記は工程全体の承認チェックで、専用ローカルでのPASSを共有環境・全対象端末・開発者承認の完了へ換算しない。実コピーの移行確認と、新設QAの受入を区別して記録する。Step 1は[PR #8](https://github.com/kosuke978/mj-stats/pull/8)でマージ済み、開発者の工程完了承認も取得済み。未確認端末・本番運用等の制限は引き続き品質文書へ残す。

対象要求はR-AUTH-01〜04、具体的な確認は [Q-06〜Q-10とQ-21](quality-and-acceptance.md)。以下は工程の完了チェックであり、Qケースの実行結果はPRに残す。

- [x] 実DBで自分のSupabase UIDと対応する `users` レコードを作成・取得できる。
- [x] 同一UIDで再度取得しても同じレコードを返し、並行初回アクセスでも重複しない。
- [x] 初回の表示名設定が必須で、名前と完了状態を保持し、直接APIアクセスでも未設定状態の制限を迂回できない。

- [x] 未ログインの保護ページ直接アクセスは `/login` に移動する。
- [x] 自己登録・メール確認待ち・有効な確認後の導線が成立し、初回名前設定へ進める。登録だけでリーグの成績閲覧・管理権限を得ない。

認証基盤のPhase 5への効果は、「誰が操作したか」を確実にする共通の入口を持てること。後から `league_members` の所属とroleを使ってリーグごとの権限を判定し、`recorded_by` 等で記録者を追える。**ログインできることは、そのリーグの管理者であることを意味しない。** Step 1だけでAdmin権限まで完成したとは報告しない。
