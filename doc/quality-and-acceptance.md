# 品質基準と受け入れ確認

この文書は「どの証拠があれば完成と言えるか」を定める。要求の正本は [requirements.md](requirements.md)、現行の挙動は [features-api.md](features-api.md)、設計条件は [architecture.md](architecture.md)、工程とDoDは [product-roadmap.md](product-roadmap.md) を参照する。

ここにあるQケースは**検証設計であり、実行済みの結果ではない**。文書整備では実DBへ読み取り接続して構造・集計を確認し、公開JWKSと開発者による署名設定の画面確認を記録した。DB書き込み・実アカウントでのログイン・アプリAPIの受入確認は行っていない。将来Stepのケースを記載しても、その実装着手を承認したことにはならない。

- コミット、実行日時、Web/APIの設定、検証DB・Authプロジェクトを識別する。秘密値は記録しない。
- DB書き込みを伴うケースは専用の検証DBとfixtureを使う。実ユーザーの履歴や本番DBを検証データにしない。
- テストユーザーA/B、異なる4参加者、ルール、必要なら2リーグ・2シーズンを固定したfixture IDで用意する。作成方法・cleanupを記録する。
- 基準スキーマは [architecture.md](architecture.md) の読み取り結果。検証環境では実体・版を照合し、PK/FK/UNIQUE、NULL、ID型の変更を確認する。今回の実データは書き込み試験のfixtureに流用しない。
- JWTの有効・無効ケースは検証用Auth環境または専用の検証鍵で作る。トークン文字列・パスワード・refresh tokenをPRやログへ貼らない。
- HTTPステータス、応答契約、DBの前後差分、画面の結果を必要な範囲で記録する。「エラーが出た」だけで不正書き込みなしと判断しない。

## Step 2以降：整合性・データ境界の受け入れ確認

## 証跡の残し方

PRには変更に関連するQケースと要求IDを示す。Qをまとめて記載しても、正常・異常・環境障害の結果は識別できるようにする。

```text
対象: Q-08 / R-AUTH-02
コミット・日時: <commit> / <実行日時・タイムゾーン>
環境: <Web/APIの起動条件、検証DB・Auth環境の識別名>
準備: <fixture・鍵方式・初回/既存の条件。秘密値は省略>
操作: <使用コマンドまたは画面操作。JWTは [REDACTED]>
期待値: <HTTP応答・対象DB差分・画面状態>
実測: <観察した値、DB件数/対応ID、必要な画像・ログの参照>
判定: PASS / FAIL / 未実施 / 前提未確定
未実施・差異: <理由、影響、対応Step、必要な開発者判断>
```

実装がある・コードを読んだ・試験を設計した・実行して合格した、の4つを分ける。未実施や前提未確定をPASSへ換算しない。自動テストを追加した場合はコマンドと実行件数を記録し、`[no test files]` をテスト合格件数として数えない。

2026-10-06の実DB調査は、構造・件数・Auth紐付け・NULL参照・現行総点/ポイント合計の観測。アプリのログイン、API保護、計算の個別再現、保存、rollback、認可のQケースは実行していない。既存19対局の総点が10万点・ポイント合計0でも、Q-11/Q-12の不正保存拒否が実装・検証済みにはならない。

## 文書の品質確認

- 要求に安定したR-ID、検証にQ-ID、開発者の判断にD-IDがあり、参照先が存在する。削除したIDを別の意味へ再利用しない。
- 現行仕様・承認済み要件・提案・未決定・未実装を区別する。完了状態は実装と証跡を伴って更新する。
- APIの入力・出力・認証・エラーとGo/Webの型が一致する。UUID、season型、名前とID、点数単位、NULLを確認する。
- リンク、ファイルパス、コマンドの実行場所、JSON例の構文を確認する。例は型説明か実行fixtureかを明記する。`git diff --check` は未追跡ファイルを含まないため、新規文書も明示的に確認する。
- DoDとQケースが対応し、判断待ちの項目は [decisions.md](decisions.md) へ集約する。同じ仕様を複数文書で独立管理しない。
- 機能・DB・API契約・運用ルールが変わるPRで対応文書も更新する。文書だけの変更に実DB確認を要求しない。

## 非機能要件で開発者が決めること

性能・可用性・保持期間は測定条件や運用費に影響するため、任意の数字を完成基準へ追加しない。利用規模と公開範囲が定まった時点で [decisions.md](decisions.md) に選択肢・根拠・決定を残す。

| 論点 | 決める内容 | 決定後の確認方法 |
| --- | --- | --- |
| 性能・容量 | 想定リーグ/参加者/対局数、同時利用、履歴の応答目標、ページングの時期 | fixtureの規模・計測環境を固定し、取得/計算/保存の時間とクエリ数を測る |
| 可用性・復旧 | 許容停止時間、バックアップ、許容データ損失、復元担当・手順 | 開発環境でバックアップから復元し、参照と主要操作を再確認 |
| データ・公開範囲 | 成績の公開単位、個人情報/ログの保持、退会や削除・訂正の扱い | 承認した操作と境界の受け入れケースを追加 |
| 対応端末・アクセシビリティ | D-39でスマホWebを承認済み。[画面仕様](features-api.md#表示と対応端末)にブラウザ・幅・操作基準を定義。実行版をPRへ記録 | Q-19/Q-26で文字切れ・入力・フォーカス・エラー認識・再訪を確認 |

Phase 3〜5の分析精度・SVG共有・精算の詳細な受け入れ基準は、各Phase着手の承認後に追加する。必要な検証が揃っても、**各PRのマージと次Stepの着手は開発者の明示承認が必要**という運用は変わらない。
