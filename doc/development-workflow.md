# 開発・ブランチ・PRの運用

## 承認済みの基本ルール

2026-10-06の開発者回答に基づく。

- `develop` は置かない。`main` と短命の作業ブランチで開発する。
- PRは原則として1 Stepにつき1本。緊急時は、影響範囲と理由をPRに記して例外を認める。作業ブランチとPRの範囲はレビューできる大きさにする。
- **各PRのマージは開発者の明示承認を必要とする。** テスト成功、レビュー完了、PR作成の依頼だけではマージ承認と扱わない。
- **次Stepへの実装着手も開発者の明示承認を必要とする。** PRのマージ承認とStepの完了承認は区別する。一度の指示で両方が明示された場合は、その範囲に従う。
- Phase 3〜5はロック中。拡張性の確保や設計提案はできるが、機能実装を先行させない。
- D-20により、まず設計確認1〜12すべてのドキュメント整備と総合レビューを終える。その後、開発者がコーディング移行を判断し、実装Step 1から進める。設計期間にアプリ実装・DB変更を先行させない。

## 作業開始からPRまで

1. ユーザーの依頼と現在Stepを確認し、該当ドキュメント・コード・`AGENTS.md` を読む。
2. `git status --short --branch` を確認し、既存の変更や未追跡ファイルを把握する。ユーザーの変更を上書き・削除・勝手にコミットしない。
3. 新しい作業は最新の `main` を起点にブランチを作る。未完了の変更がある場合は、別worktreeなどで分離する。未マージPRに依存する場合は、その依存をPRに明記する。
4. 目的、変更範囲、完了条件を整理する。データの識別・公開範囲・権限・履歴に影響する判断は、選択肢と推奨理由を示して開発者に決めてもらう。
5. 実装、必要な検証、対応する文書の更新を行う。小さな複数変更をまとめた場合は、各機能の変更点と確認結果を記載する。
6. 差分を読み直し、不要なファイル・デバッグ出力・秘密情報を除く。対象ファイルを指定してコミットする。
7. 依頼範囲に応じてpush・PR作成まで進める。実装途中や判断待ちはDraft PRにする。
8. 承認を得たPRを合意した方式でマージし、必要ならStepの完了報告を行う。

`main` に直接コミット・pushしない。ブランチを切ることや通常の作業を、毎回の許可待ちにしない。一方、マージ・次Step着手は承認済みルールに従う。

## ブランチ名

形式は `<type>/<短い英語の目的>`。小文字とハイフンを使う。既存履歴には `feature/` と `feat/` が混在するが、新規ブランチは以下へ揃える。既存名の一括変更は行わない。

| type | 用途 | 例 |
| --- | --- | --- |
| `feat` | 新機能・機能の完成 | `feat/auth-api-protection` |
| `fix` | 不具合修正 | `fix/match-history-user-id` |
| `refactor` | 挙動を維持した構造整理 | `refactor/match-point-calculation` |
| `docs` | 文書の追加・更新 | `docs/project-documentation` |
| `test` | 独立した検証基盤・テストの整備 | `test/auth-validation` |
| `chore` | 依存関係・設定・開発基盤 | `chore/api-ci` |

1機能の完成に必要なAPI・画面・DB・文書は同じブランチに含めてよい。`api` / `web` というフォルダだけを理由に分けない。小規模な複数機能なら、全体の目的を表す名前にしてPR本文に内訳を書く。規模の大きい変更や別々のリリース判断が必要な変更は分ける。

作業ツールにブランチ名の指定がある場合は、その指示を優先する。禁止対象の次Step実装を「小さいから」と同じブランチへ含めない。

## コミット

推奨形式は `type(scope): 内容`。内容は日本語でもよい。scopeは `auth`, `api`, `web`, `match`, `docs` 等、レビューに役立つ範囲だけ付ける。

```text
docs: プロダクト方針と開発運用の文書を整備
feat(auth): 保護APIでSupabase JWTを検証
fix(match): 履歴の参加者IDと表示名を分離
```

- コミットは機能ごとを目安に、実装と対応する試験をまとめて柔軟に分ける。整形だけの大量差分を機能変更へ混ぜない。
- API互換性・DB移行に影響する変更は、コミット本文とPRで具体的に記す。
- `.env`、トークン入りPostman環境、生成バイナリ、`.DS_Store`、ビルド成果物を追加しない。作業開始時に見つけた既存の未追跡ファイルはそのまま残す。
- push済みの共有ブランチを書き換える操作は、共同作業への影響を確認する。`main` へのforce pushは行わない。

## PRの形

baseは `main`。タイトルは最終的な変更を表し、例として `docs: MJ-Statsの仕様・開発運用を文書化` や `feat(auth): JWT検証と対局APIの保護を完成` を使う。将来Phaseの名前だけでタイトルを付けない。

本文は以下を基本とする。小さな文書変更なら短くし、API・DB・認証の変更では必要な情報を埋める。複数の小変更をまとめた場合は「変更内容」と「確認結果」で各変更を識別できるようにする。

````markdown
## 目的と結果

どの操作・状況で何が問題になり、このPRでどう変わるか。

## 変更内容

- 利用者から見た動作と、レビューに必要な設計上の変更。
- 対象Step、関連Issue（ある場合）、関連する判断事項。

## 確認結果

- 実行したコマンドと結果。
- 対応する要求IDとQケース、期待値と観察結果。
- 手動確認した操作、環境、DBの確認結果。
- 未実施の確認と理由。単なる「動作確認済み」で終わらせない。

## 影響・残る事項

- API互換性、環境変数、DB移行・既存データへの影響。
- 残る負債、必要な追加判断、運用上の制約。
- 必要な場合の適用順序と戻し方。

## 承認

- [ ] 開発者の明示的なマージ承認
- [ ] Step完了を申請する場合は、完了条件の証跡と次Step着手の承認を別途確認
````

承認欄は自己申告で完了させず、実際の開発者の指示・レビューコメントに基づいて更新する。文書を更新した場合は該当箇所をリンクする。スクリーンショットやAPI例は、見た目・契約の確認に必要なときに添付する。

既存の `.github/PULL_REQUEST_TEMPLATE.md` とCI workflowはない。この本文は手動で使える規約であり、GitHub上にテンプレートや必須チェックを設定済みという意味ではない。

## 検証とレビュー

検証は変更の影響に合わせる。変更別のコマンド、要件に対応するQケース、証跡の形式は [quality-and-acceptance.md](quality-and-acceptance.md) を正本にする。PRで該当する要求IDとQケースを示し、実行結果・未実施理由を記録する。コードを変えない文書更新に、実DB書き込みや全アプリのテストを義務付けない。

レビューでは、依頼の達成、現在Stepの範囲、ゲストや履歴の永続ID、Goでの検証・認可、API/DB/Webの整合、検証の証拠、文書更新を確認する。必要なチェックが通った後に、理由なく同じ検証を繰り返さない。

## マージとStep完了

マージ前に、競合なし、対象変更に必要な検証完了、レビュー指摘の解消、開発者の明示承認を確認する。GitHubのブランチ保護や必須チェックは設定を未確認のため、このルールが自動で強制されるとは考えない。

**マージ方式はSquash merge（D-10、2026-11-17承認済み）。** PRを1コミットへまとめ、タイトルと本文から変更・検証・影響を辿れるようにする。既存のMerge commit履歴を書き換えない。各PRの明示的なマージ承認は引き続き必要で、自動マージは有効化しない。GitHubの許可方式・保護設定を変更済みという意味ではない。

2026-11-20にmainの履歴を照合したところ、Phase 2.5のPR #8〜#13はいずれも2親のMerge commitでマージされていた。D-10の方式を見直す場合は開発者が判断する。

マージ後は、実装内容、確認結果、残る負債、最終構想への影響を報告する。Step完了時は [Definition of Done](product-roadmap.md) を照合し、開発者に完了と次Step着手を判断してもらう。マージ済みブランチは共同作業が終わったことを確認して整理する。

## AIエージェントとの作業

- 現在の依頼の範囲で、調査・文書・実装・必要な検証を自律的に完了する。提案だけで作業を終えない。
- 仕様に必要な判断は早めに選択肢を出す。返答待ちでも、判断に依存しない調査・実装準備を進める。
- D-23に従い、互いに独立した論点をまとめて提示する。各論点の推奨と影響を示し、一括採用・番号指定で回答できる形にする。先の回答で後の選択肢が変わるものはタイミングを分ける。事実の未確認を推奨で埋めない。
- 推奨案、開発者の決定、実装済みの状態を分けて報告し、決定を [decisions.md](decisions.md) に残す。
- 未依頼の本番反映、履歴を壊すDB変更、マージ、次Step実装を行わない。必要な承認は、具体的な差分・検証・影響を揃えてから求める。
- シークレットやユーザーの作業成果を保護し、無関係な変更を巻き込まない。
- Phase 3〜5への設計上の効果を説明する。現在の機能だけを優先して、参加者ID・ルール履歴・SVG出力の余地を失わせない。
