# MJ-Stats ドキュメント

MJ-Statsは、サークルや麻雀コミュニティの対局を記録し、深い成績分析とSNSへの画像共有で楽しめるアプリを目指す。

このフォルダは、プロダクトの方針、既存実装の仕様、開発・運用手順の入口。現在は **Phase 2.5 / Step 2「リーグ・ルール基盤」**。Step 1は完了承認済み、2-1はPR #9でマージ済み。開発者の指示を受け、2-2のルール・シーズン・対局帰属のDB基盤を実装した。Step 2全体は途中。工程は [ロードマップ](product-roadmap.md)、検証は [品質文書](quality-and-acceptance.md) を参照する。リポジトリの入口は [ルートREADME](../README.md)、AI向けの入口は [AGENTS.md](../AGENTS.md)。

## 文書の更新ルール

- 実装が変わるPRで、対応する仕様・API例・手順を同時に更新する。
- 要件は `requirements.md`、設計は `architecture.md`、現在の挙動は `features-api.md`、工程は `product-roadmap.md`、判断は `decisions.md`、検証は `quality-and-acceptance.md` を正とする。同じ詳細を複数箇所で独立管理しない。
- 要件のR-ID、確認ケースのQ-ID、判断のD-IDをPRで結び付ける。例：`R-AUTH-03 → D-03 → Q-06/Q-07 → 実行結果`。IDがあるだけでは達成とは扱わない。
- 方針と実装が食い違う場合、方針を黙って緩めず、実装側の負債として記録する。
- 完了状態を変えるときは、確認した環境・結果と開発者の承認を残す。調査日だけを更新して未確認事項を確認済みにしない。
- 秘密情報、アクセストークン、実際の接続パスワード、個人のメールアドレスを文書・PR・Postman exportへ載せない。

担当は当面、開発者が要件・判断の承認、変更を行う開発者またはAIが該当文書の更新、レビュー担当が整合と証跡の確認を担う。日常の結果・作業ログはPRへ残し、恒久的な仕様や決定だけをこのフォルダへ反映する。

### 変更したときの更新先

| 変更 | 主に更新する文書 | 条件付きで更新する文書 |
| --- | --- | --- |
| 業務ルール・権限・公開範囲 | 要件、判断、品質・受入 | 設計、API、対象工程が変わればロードマップ |
| DB型・制約・参照・移行 | 設計のデータ辞書、環境・運用、品質・受入 | API型や業務条件も変わる場合は機能・API、要件 |
| API入出力・認証・エラー | 機能・API、品質・受入 | 設計、設定が増える場合は環境・運用 |
| 画面の操作・状態・遷移 | 機能・APIの画面仕様、品質・受入 | 目標動作が変わる場合は要件、重要な仕様選択は判断 |
| 環境変数・起動・デプロイ・復旧 | 環境・運用 | 検証手順も変わる場合は品質・受入、構成変更なら設計 |
| 完了判定・実装状況 | 現行仕様、ロードマップ。実行証拠はPR | 状態が変わる要件、判断の実装影響 |

影響する文書だけを更新する。文書を変更しない場合も、PRで既存仕様と一致していることを説明できればよい。作業前の設計メモはPR/Draftまたは依頼への説明へ置き、恒久的な正本に必要な内容だけを反映する。
